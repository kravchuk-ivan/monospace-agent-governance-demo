# Monospace study guide (verified hands-on on v1.1.0, 2026-11-17)

Everything below was observed on the running instance in this repo unless marked *(docs)*.

## 1. What it is, in one breath

A governed API layer that connects the databases (and, through connector extensions, the APIs) a company already runs. It queries them live and serves one permissioned API, as REST, a typed TypeScript SDK and MCP, to every app, person and agent. Admin UI: **Studio**.

## 2. Architecture you can point at

| Piece | What it is here |
|---|---|
| Engine | Rust (the logs show `axum`/`aide`). Image `monospace/monospace:v1.1.0`, port 8100 |
| System DB | Its own Postgres for users, roles, policies and schema metadata. Separate from customer data |
| Redis | Query result cache (reads cached by default) |
| RabbitMQ | Event bus: email and cluster metadata sync across replicas |
| Studio | Web admin UI served by the same container |
| Keys | JWT signing (Ed25519) and KMS master key, generated by an init container |

Jonathan's numbers: Kubernetes in production, 200 ms API target, load queued rather than erroring, typical org 5–10 workspaces × 12–24 sources.

## 3. The object model

```
Organization ── users, service accounts, API keys, license
 └─ Workspace (apiName → URL segment /api/<ws>/...)     Starter: 1
     ├─ Data sources: postgres · mysql · mariadb · sqlserver (1.1) · connector extensions (preview)
     │    └─ access flags: allowMigrations / allowCreate / allowUpdate / allowDelete
     │    └─ collections + fields, introspected (snake_case DB → camelCase API names)
     ├─ Relations, including ACROSS sources (metadata only, no FK written)
     ├─ Roles (flat, no inheritance) ── built-in: Administrator, Public
     │    └─ Policies (JSON documents, attachable to many roles)
     └─ MCP server: POST /api/<ws>/mcp
```

## 4. Permissions: the policy document

A policy is either `{"access":"admin"}` or `{"access":"rules", ...}` with four parts:

| Part | Shape | Example in this repo |
|---|---|---|
| `itemRules` | per collection, per action (`read/create/update/delete`): `{}` = all rows, `{"filter":{...}}` = row filter | front desk: `patients.read.filter = {clinicId:{_eq:1}}` |
| `fieldRules` | per collection, per action (`read/create/update`): `"*"` or `{field: {}}` (optionally `{filter}` per field) | billing: `paymentMethods.read` = brand, last4 only |
| `validationRules` | per collection: filters the **written payload** must satisfy | billing: `refunds.amount _lte 200` |
| `entitlements` | strings like `ai:mcp`, `dataModel:read`, `dataModel:edit`, `dataSource:read:*`, `role:read:*` | both agents: `ai:mcp`, `dataModel:read` |

Built-in policies on a new workspace: **Admin** (`access: admin`) and **Studio access** (read the data model, members, settings, sources, roles and policies).

Filters use underscore operators: `_eq _neq _in _nin _lt _lte _gt _gte _null _contains`, `_and/_or/_not`, and `_some/_every/_none` on to-many relations.

## 5. Two layers of control (a good whiteboard point)

1. **Source access flags.** They apply to *every* caller, admins included, and remove the operation from the query schema (`deleteOne operation not found`). A schema lock refuses migrations (`the database schema of data source Payments is locked`). **Works on Starter.**
2. **Identity → role → policy.** Per user or service account: rows, fields, write validation and entitlements. **Needs a license** (Starter: 0 custom policies, roles and service accounts).

## 6. Identity and keys

- An API key **acts as its user**. It has no scope of its own, so to scope an agent you give it its own identity (a service account) with its own role.
- `POST /api/system/api-keys {name, userId, ttl}`, where `ttl` is `"1h"`, `"7d"`, `"30d"`, or `null` for never expires.
- `PATCH /api/system/api-keys/:id {active:false}` returns 401 on the next call. `DELETE` revokes permanently.
- The MCP caller needs the `ai:mcp` entitlement. Anonymous MCP gets 403 unless someone grants it to the Public role.

## 7. Interfaces

| | How |
|---|---|
| REST | `/api/<ws>/items/<collection>?fields=a,b&filter[x][_eq]=1&include[rel][fields]=c&sort[0][x][direction]=asc` |
| OpenAPI | `GET /api/<ws>/openapi` (item routes, per workspace, generated from the live schema) |
| SDK | `npx monospace sdk generate` → `createClient({url, workspace, apiKey})` → `client.patients.readMany({fields, filter, include})`, fully typed |
| MCP | 7 tools: `list_items create_items update_item delete_item read_schema read_data_sources mutate_schema`. The list is the same for everyone; **each call is checked** |
| CLI | `@monospace/cli`: `login`, `whoami`, `sdk init/generate`, `extension create/build` |

Gotchas: there are no aggregates, no full-text `search` and no cursor paging (use limit and offset). 64-bit ints and decimals come back as strings. Deletes need a `fields` selection.

## 8. License tiers (from `/api/system/license` on this instance)

Starter (keyless): workspaces 1, seats 3, custom roles 0, custom policies 0, service accounts 0, SSO off, custom permission rules off, audit logs off, premium and custom connectors off, telemetry required. Business and Enterprise: custom pricing *(docs)*. With a key, the instance activates online against `licensing.monospace.io`, tied to `MONOSPACE_BASE_URL` *(starter docs)*.

## 9. Positioning cheat sheet

- **vs MCP gateway:** the gateway sees the call, Monospace sees the data (builds the query, so it decides the rows).
- **vs warehouse (Snowflake etc.):** analytics on a copy. Monospace is live read-write on the system of record.
- **vs iPaaS (MuleSoft, Workato):** sync in the background. Monospace is called at request time.
- **vs Hasura / Supabase / PostgREST:** mostly single database. Monospace federates many sources with one permission model.
- **vs Denodo / Starburst:** federation for analytics. Monospace is federation for operational apps and agents.
- **vs Directus:** Directus is one SQL database with a CMS heritage. Monospace is many sources with enterprise governance (and a different API and SDK).

## 10. Product observations from building this (bring one or two, framed as questions)

Found in one evening of self-serve setup. Each is something a prospect's engineer would hit.

1. **Activation:** the headline use case (per-agent least privilege) can't be experienced on the free tier. Starter has 0 custom policies and 0 service accounts, so an evaluator sees governance only after talking to sales. *Question:* is that deliberate gating, or would 1–2 custom policies on Starter lift activation?
2. **The engine validates a policy before checking the license** (a valid one gets 402, a bad one 422). That's the core of an **access preview / dry-run** endpoint: "show me what this agent would see before I grant it". CISOs ask for exactly that.
3. **OpenAPI vs engine mismatch:** the system OpenAPI describes field rules as `"Wildcard"` or `{"Rules":{...}}`, but the engine accepts `"*"` or `{field:{}}`. This looks like Rust serde enum names leaking into the schema. Anyone generating clients from the spec gets 422s.
4. **Automation surface:** first-admin creation (`POST /api/system/bootstrap`) and list routes (`GET /api/system/api-keys`, `GET /api/<ws>/roles`) work but aren't in the OpenAPI document. Repeatable demo and CI environments need them, and an SE team building demo templates would use them daily.
5. **Agent-facing errors:** "deleteOne operation not found … Query validation failed" is accurate, but an agent recovers better from "deletes are disabled on source EHR". `delete_item` without `fields` returns "missing field `fields`".
6. **Naming:** introspected fields become camelCase, but relation names keep the table names (`billing_accounts`, `payment_methods`). The inconsistency shows up in what an agent sees.
7. **Read auditing:** the docs list auth events and role and policy changes. For HIPAA, the question is whether the log records which records an agent *read*.
8. **Key hygiene:** keys can be created with `ttl: null` (never expire). Security buyers will ask for an org-level max TTL for service-account keys.

## 11. API calls worth remembering

```bash
# system
GET  /api/system/info                     # version, onboarding, license status
GET  /api/system/license                  # entitlements + usage
POST /api/system/workspaces               {apiName, displayName}
POST /api/system/api-keys                 {name, userId, ttl}
POST /api/system/service-accounts         {fullName}
# workspace
POST /api/<ws>/sources/data               {apiName, provider, host, port, user, password, dbname, access}
POST /api/<ws>/schema/migrate             {operations:[{kind:'createRelationFieldPair', ...}]}
POST /api/<ws>/policies                   {name, content}
POST /api/<ws>/roles                      {name}
POST /api/<ws>/roles/<id>/policies        {policyId}
POST /api/<ws>/service-accounts           {serviceAccountId, roles:[...]}
POST /api/<ws>/mcp                        JSON-RPC, Accept: application/json, text/event-stream
```
